# OG-CLOSE1 — OG image generation / cache / deploy closure

Date: 2026-08-20
Status: OPEN / GREEN / BRANCH
Branch: `chore/og-closure-1`
Base: `a1853f113bb76efe9a065aae4b1c09fed0234dfd`

## Scope

This closure addresses OG image generation, cache ownership, and production consumption only.

Unchanged by design:

- Canonical Content v1
- Timeline projection (`T1B2`, `T1B3`)
- PF5
- Presentations architecture
- Media architecture

## Primary finding

Observed log line:

`[11ty] Writing og-cache/<hash>.png from ./src/og-image.og.njk`

Conclusion:

- This log line indicates a real PNG render+write, not bookkeeping.
- The plugin still renders OG template HTML on warm runs to compute the deterministic hash.
- Warm runs skip PNG byte writes when the cache hit already exists.

This was verified from the installed `eleventy-plugin-og-image` implementation:

- output filename is derived from a hash of rendered OG HTML + render options
- the plugin checks whether the output file already exists
- only a missing output file triggers Satori/Resvg/Sharp rendering and PNG write

## Before pipeline

Current pre-closure pipeline on `main`:

canonical page data
→ `base.njk` always invokes `ogImage`
→ `eleventy-plugin-og-image`
→ `og-cache/<hash>.png`
→ `.eleventy.js` copies the whole `og-cache` directory into `_site/og-images`
→ separate GitHub workflow `Generate OG Images`
→ GitHub Actions cache only

Production deploy path before closure:

`build.yml`
→ `npm run build:no-og`
→ no OG generation
→ no `og-cache` restore
→ no `_site/og-images` publish path sourced from generated cache

Consequences:

- isolated `Generate OG Images` workflow had no direct production consumer
- production deploy did not prove ownership of generated OG assets
- pages with explicit OG images/thumbnails still paid unconditional `ogImage` generation cost
- stale cache entries survived indefinitely and could be recopied into deploy output

## Selected architecture

Selected option: **A. persisted generated assets**

Reason:

- page-specific generated OG images remain useful (`1081` unique generated assets actively referenced)
- one static fallback image would regress the branded/page-specific fallback behavior
- the smallest coherent closure is to keep deterministic generated assets, make production build the only consumer path, and prune non-current cache/output entries

## After pipeline

Post-closure pipeline:

canonical page data
→ `base.njk` invokes `ogImage` only when no authoritative page-specific OG image is already available
→ `eleventy-plugin-og-image`
→ deterministic `og-cache/<hash>.png`
→ production `build.yml` restores `og-cache`, runs `npm run build`
→ `.eleventy.js` scans built HTML for referenced `/og-images/*`
→ only referenced generated files are copied into `_site/og-images`
→ unreferenced cache files are pruned
→ production deploy consumes `_site/og-images` directly

Event model after closure:

### PR to `main`

`staging.yml`
→ `npm run build:no-og`
→ zero generated OG PNG writes
→ HTML / SEO / Pagefind / staging verification only

### Production push to `main`

`build.yml`
→ restore `og-cache`
→ `npm run build`
→ generate missing/changed OG images only
→ sync referenced generated assets into `_site/og-images`
→ deploy the same `_site` tree

## Closure changes

### 1. Guard generation to real fallback consumers only

`src/_includes/base.njk`

- moved `ogImage` invocation behind the existing image-selection logic
- generated fallback runs only when:
  - no explicit `og_image` / `ogImage` / `ogImageOverride`
  - no trusted page thumbnail is eligible

### 2. Sync only referenced generated OG assets

`.eleventy.js`

- scan built HTML for referenced `/og-images/<hash>.*`
- copy only referenced files from `og-cache` to `_site/og-images`
- fail the build if HTML references a generated OG file missing from cache
- prune stale `og-cache` files after each generating build

### 3. Remove isolated no-consumer workflow

Deleted:

- `.github/workflows/og-images.yml`

Updated:

- `.github/workflows/build.yml`
  - restore `og-cache`
  - run `npm run build`
  - deploy the same `_site` tree that now contains referenced generated OG assets
- `.github/workflows/staging.yml`
  - run `npm run build:no-og`
  - do not restore `og-cache`
  - validate HTML / SEO / staging output without materializing generated OG PNG assets

## Production consumer proof

The production consumer path is now explicit and closed:

1. `build.yml` restores deterministic `og-cache`
2. `build.yml` runs `npm run build`
3. `.eleventy.js` copies only currently referenced generated files into `_site/og-images`
4. `_site` is uploaded as the Pages artifact
5. deployed HTML points at `https://www.jarilaru.fi/og-images/<hash>.png`

PR validation path intentionally differs:

1. `staging.yml` runs `npm run build:no-og`
2. OG shortcode returns `null`
3. `base.njk` falls back to `/img/WIN_20210329_16_06_01_Pro.jpg` when no authoritative page image exists
4. pages with authoritative thumbnails or explicit overrides keep their canonical image URLs
5. staging artifact stays internally valid without generated `_site/og-images`

Representative proof during measurement:

- `/tietoa/` referenced `https://www.jarilaru.fi/og-images/5d3da2d9.png`
- after one title change it referenced `https://www.jarilaru.fi/og-images/3def5865.png`
- both `og:image` and `twitter:image` moved together with the deterministic hash

## Stale/orphan policy

Explicit policy after closure:

- `og-cache` is a deterministic reusable build cache, not a permanent archive
- PR validation does not restore or require `og-cache`
- production is the only routine workflow that materializes generated OG assets
- after each generating production build, files not referenced by current built HTML are deleted from `og-cache`
- `_site/og-images` in the production build is the deployable generated asset set

## Scope conclusion

OG-CLOSE1 closes the missing production-consumer path, removes the isolated no-consumer workflow, keeps generated assets out of routine PR builds, prunes stale production-generated assets, and reduces cold-generation output from `1292` to `1081` by skipping pages that already have authoritative OG imagery.
